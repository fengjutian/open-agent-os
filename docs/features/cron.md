# 定时任务（cron）

> 对标：Octop 的 `api/routers/cron`（每个 Agent 一组 cron job）
> 状态：**已实现**

## 1. 要解决什么

"每天 9 点让 Agent 汇报一次进展"这类需求，不应该靠外部 curl + 系统 crontab 拼。
任务定义、排期、执行记录都应该在平台内，并且能在界面上看见。

## 2. 语义

- 表达式是**标准 5 段 cron**（分 时 日 月 周），支持 `*`、数字、范围 `a-b`、
  步长 `*/n` 与 `a-b/n`、列表 `a,b,c`，以及 `@hourly` / `@daily` / `@weekly` / `@monthly`；
- **按 UTC 解释**。多时区需求由调用方自行换算表达式——先把语义钉死，比含糊地猜本地时区安全；
- 日与周字段都被限定时，沿用标准语义：**满足其一即可**（例如 `0 0 13 * 5` = 13 号或周五）。

## 3. 三个关键设计

**① 先推进、后执行。** 命中任务时先把 `next_run_at` 算到下一次并提交，再真正执行。
即使执行阶段崩溃，下一轮 tick 也不会重复触发同一条任务。

**② 状态用独立会话回写。** 运行失败时业务事务会回滚，如果状态写在同一事务里就会丢。
所以执行用一个会话、状态回写用另一个会话——失败也要留下 `last_status=failed` 和错误原因。

**③ 执行前必须切租户上下文。** 调度循环跑在请求之外，`current_tenant()` 默认是 `default`；
不切上下文的话，B 租户的任务会查不到自己的 Agent。查询到期任务时用
`include_all_tenants=True` 跨租户取，执行时再 `set_tenant(job.tenant_id)`。

## 4. 明确不做 / 已知限制

- **进程内轮询，不是分布式调度**。多实例部署会重复执行同一条任务，
  需要外部锁（例如 Redis 租约）才能真正安全。这里不假装支持。
- **不补跑错过的所有历史**：停机很久后，一条任务只会执行一次并把排期推进到未来，
  避免一次刷出几百条运行。
- 不提供秒级精度；最小粒度是分钟。
- 不做时区转换，表达式一律 UTC。

## 5. 实现位置

| 关注点 | 位置 |
|---|---|
| 表达式解析与下次时间计算 | `backend/app/services/cron.py` |
| 执行、状态回写、调度循环 | `backend/app/services/cron_scheduler.py` |
| 模型 | `backend/app/models/entities.py` `CronJob` |
| 接口 | `backend/app/api/cron_routes.py` |

| 前端 | `frontend/src/panels.tsx` `CronPanel`、`App.tsx` 的「定时」视图 |

## 6. 测试

- 表达式：步长、每天、每月、周几语义、日/周"或"语义、别名、六种非法输入；
- CRUD：创建/列表/改排期重算/删除/权限/审计/跨租户不可见；
- 执行：`run-now` 落消息；到期任务执行一次并推进排期；同一时刻再跑不重复；
  停用不执行；Agent 被删后记录 `failed` 且错误可读；
- 跨租户：B 租户的任务只写进 B 的会话，默认租户查不到；
- 真实服务：`CRON_TICK_SECONDS=2` + `*/1 * * * *`，60 秒内观察到自动执行、
  `next_run_at` 自动推进、会话里出现助手回复。
