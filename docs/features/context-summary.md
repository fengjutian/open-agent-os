# 上下文压缩（历史摘要）

> 对标：Octop 的 `infra/agents/memory/slim.py`、harness 的 compaction
> 状态：**已实现**

## 1. 要解决什么

`context_max_chars`（默认 24000）决定了单次请求能带多少历史。原来的策略是
**从最旧的消息开始整条丢弃**——历史一长，最老的内容整段消失，用户会明显感到
"Agent 失忆"：前面说过的约束、偏好、结论全都问不出来。

摘要替代丢弃：把装不下的那部分历史压成一段要点，和最近若干条消息一起送进模型。

## 2. 触发与边界

三个条件同时满足才会摘要：

1. 历史总长度超过预算的 `CONTEXT_SUMMARY_TRIGGER_RATIO`（默认 0.8）；
2. 尚未被摘要覆盖的消息数量 **≥ 保留条数**（`CONTEXT_SUMMARY_KEEP_MESSAGES`，默认 6）；
3. 摘要功能开启（`CONTEXT_SUMMARY_ENABLED`，默认开）。

第 2 条是防抖：否则每轮都只多一条消息，却要重新摘要一次，纯属浪费。

保留最近 `keep` 条消息**原样不动**——最近的上下文对连贯性最重要，不该被摘要改写。

## 3. 三个刻意的取舍

**① 摘要失败不影响对话。** 摘要是一次额外的模型调用，可能超时、报错、返回空。
失败时记录 warning 并退回"整条丢弃"，对话照常进行。宁可忘事，也不能因为摘要挂掉。

**② 摘要随会话持久化，只摘要增量。** `conversations.summary` 存摘要文本，
`summary_message_count` 记录已经覆盖到第几条历史。下一轮从这条线之后继续，
不会重复花钱。启动时也不需要预热。

**③ 摘要放在 system 之后、历史之前。** 它代表"更早的对话"，语义上属于背景，
不该伪装成用户发言（否则模型会把它当成新的指令）。

## 4. 成本与失败面

- 每次摘要是一次额外的模型调用，输入是待压缩的那段历史（超过 `max_chars * 6` 时先截断）；
- 摘要长度上限 `CONTEXT_SUMMARY_MAX_CHARS`（默认 2000），避免摘要自己把预算吃满；
- 摘要调用**不计入 run 的 token 统计**（它不是一次运行），但会计入模型成本——
  这是已知的观测盲区，接真实计费时要补。

## 5. 实现位置

| 关注点 | 位置 |
|---|---|
| 摘要调用与提示词 | `backend/app/services/summarizer.py` |
| 触发判断、持久化、失败回退 | `backend/app/services/agent_runtime.py` `_ensure_summary` |
| 上下文拼装（摘要进 system） | `backend/app/services/context.py` `build_messages(..., summary=...)` |
| 字段 | `Conversation.summary` / `Conversation.summary_message_count` |

## 6. 测试

- 纯函数：带摘要时 system 里出现 `[早前对话摘要]`，不带时行为不变；
- 长历史：触发一次摘要，摘要落库，回答请求里带上了摘要；
- 复用：第二轮不再摘要，但摘要仍进入上下文；
- 短历史：不触发、不调模型、不落库；
- 失败：摘要报错时对话仍成功，且不写入半截摘要；
- 关闭开关：不触发。

## 7. 明确不做

- 不做向量检索式记忆（那是"长期记忆"，另一件事）；
- 不做摘要的人工编辑/审阅；
- 不做跨会话的摘要共享；
- 不按 token 精确计数（仍是字符预算，见 `context.py` 的说明）。
